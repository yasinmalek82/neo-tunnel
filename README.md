# NEO Tunnel

یک تانل Reverse با مسیر اصلی TCP/TLS، پشتیبان QUIC و ورودی ثابت TCP در ایران. منو و پیام‌های ترمینال انگلیسی‌اند. داشبورد خصوصی به فارسی نمایش داده می‌شود.

## نصب در دو مرحله

1. روی ایران، فایل `install.sh` را از [انتشار پایلوت](https://github.com/yasinmalek82/neo-tunnel/releases/tag/v0.2.1) بگیرید و با `sudo bash install.sh` اجرا کنید. در سرورهایی که با root وارد شده‌اید، `bash install.sh` کافی است. گزینهٔ `Set up Iran` آدرس ایران، پورت ورودی و پورت برنامه در خارج را می‌پرسد و دستور یک‌خطی نصب خارج را می‌دهد.
2. همان دستور را روی خارج اجرا کنید. برنامهٔ مقصد باید روی پورت loopback انتخابی در خارج گوش دهد. از منوی ایران `Manage tunnel` سپس `Status` را باز کنید و آماده‌شدن هر دو مسیر را ببینید.

نصاب برای Debian 12/13 و Ubuntu 24.04/26.04/26.10 با systemd و cgroup v2، در معماری‌های amd64 و arm64 طراحی شده است. روی ایران برای ارتباط خارج، TCP 17000 و UDP 17011 را در دسترس بگذارید. TCP 17005 موقت و برای دریافت تنظیمات است. لینک ۱۵ دقیقه اعتبار دارد، یک بار تنظیمات صادر می‌کند و باید خصوصی بماند. از `sudo neo-tunnel issue-link` می‌شود لینک تازه گرفت. کلیدهای خصوصی خارج روی خود آن سرور ساخته می‌شوند.

اگر سرور دانلود مستقیم ندارد، `install.sh`، فایل `SHA256SUMS` و آرشیو معماری همان سرور را با هم منتقل کنید. روی ایران از `bash install.sh --bundle /path/to/bundle` استفاده کنید. روی خارج `bash install.sh --bundle /path/to/bundle` را اجرا کنید و لینک خصوصی را در گزینهٔ `Join foreign server` وارد کنید. حالت `--join-stdin` نیز لینک را از stdin می‌پذیرد. جفت‌سازی حتی با بستهٔ آفلاین به دسترسی خارج به پورت موقت ایران نیاز دارد.

## مانیتورینگ و گزارش

وقتی اولین مسیر روی ایران آماده شود، ابزار به‌طور پیش‌فرض یک دورهٔ هفت‌روزه را آغاز می‌کند. دوره پس از ری‌استارت ادامه دارد و بعد از پایان خودکار دوباره شروع نمی‌شود. در نصب‌های نسخهٔ 0.2.0، اجرای [نصاب نسخهٔ جدید](https://github.com/yasinmalek82/neo-tunnel/releases/tag/v0.2.1) با `sudo bash install.sh --install-only` فقط برنامهٔ مدیریت و سرویس‌های پایش فعال را به‌روزرسانی می‌کند. اگر از قبل دوره‌ای ثبت شده باشد، وضعیت همان دوره حفظ می‌شود.

```sh
sudo neo-tunnel pilot status
sudo neo-tunnel pilot stop
sudo neo-tunnel pilot export
```

برای خاموش‌کردن، در منوی `Pilot report` گزینهٔ `Stop pilot and disable automatic start` را بزنید یا `pilot stop` را اجرا کنید. حتی اگر اتصال خارج هنوز آماده نشده باشد، این انتخاب ثبت می‌شود. دادهٔ جمع‌شده قابل خروجی‌گرفتن است و برای دورهٔ تازه بعداً می‌توانید `pilot start` را دستی بزنید. پایش از سنجش‌های موجود استفاده می‌کند و آزمون بار با `calibrate` و به درخواست شما اجرا می‌شود.

برای داشبورد، گزینهٔ `Open dashboard` دستور SSH را چاپ می‌کند. شکل آن روی کامپیوتر شما چنین است.

```sh
ssh -N -L 8787:127.0.0.1:8787 USER@IRAN_HOST
```

مرورگر را روی [داشبورد محلی](http://127.0.0.1:8787/) باز کنید. داشبورد به loopback محدود است، تغییر تنظیمات انجام نمی‌دهد و درخواست مرورگر معادل اجرای تست شبکه نیست. برای دانلود گزارش، پس از ساخت فایل روی پیوند «دانلود گزارش» کلیک کنید.

قابلیت بررسی سرویس در نصاب عمومی، دسترسی به پورت TCP مقصد را اندازه می‌گیرد. برای سنجش جواب برنامه، از پیکربندی دستی HTTP در ادامه استفاده کنید. در نمونهٔ آزمایشی، HAProxy اتصال‌های جدید TCP را جابه‌جا می‌کند. هر حامل فوروارد UDP خصوصی خودش را دارد.

## ساخت و فرمان‌ها

```sh
make test vet linux
make build
```

خروجی‌های `neo-tunnel` و `backhaul-probe` برای Linux amd64 و arm64 در `build/linux-*` قرار می‌گیرند. ابزار با Go 1.26 ساخته می‌شود و وابستگی Go خارج از کتابخانهٔ استاندارد ندارد.

```sh
neo-tunnel status --json
neo-tunnel calibrate standby
neo-tunnel apply PROPOSAL_ID
neo-tunnel rollback
```

فرمان‌های مدیریتی نصب systemd را با کاربر سرویس اجرا کنید، برای مثال `sudo -u neo neo-tunnel status --json`. مسیر پیش‌فرض تنظیم کنترل‌کننده `/etc/neo-tunnel/controller.json` است. همهٔ فرمان‌ها `--config FILE` می‌پذیرند. `watch` روی ایران بازیابی عملیات ناتمام، ثبت تغییر سلامت، مشاهدهٔ پس از اعمال و تعویض مبتنی بر شواهد تکرارشده را انجام می‌دهد. برای دریافت خروجی ماشینی به فرمان‌های مدیریتی `--json` بدهید.

## نصب دستی روی پورت آزمایشی

1. روی هر دو میزبان cgroup v2 و systemd فعال باشد. باینری‌های مناسب معماری را در `/usr/local/bin` و HAProxy را در مسیر unit نصب کنید. unitهای نمونه در [examples/systemd](examples/systemd) و راه‌انداز frp در [deploy/frp-run](deploy/frp-run) هستند. کاربر و گروه سیستمی `neo`، دایرکتوری تنظیمات و زیرشاخهٔ `runtime` را ایجاد کنید. فقط زیرشاخهٔ runtime و state به دسترسی نوشتن کاربر `neo` نیاز دارند.
2. فایل‌های `frps-*.toml` روی ایران و `frpc-*.toml` روی خارج قرار می‌گیرند. آدرس و SAN گواهی ایران و پورت واقعی برنامهٔ مقصد را تعیین کنید. برای frp از گواهی‌های دوطرفه و توکن مستقل هر مسیر استفاده کنید. پورت‌های 17000/TCP و 17011/UDP از خارج به ایران لازم‌اند. پورت‌های فوروارد و متریک روی loopback می‌مانند.
3. روی هر میزبان از [agent.json](examples/agent.json) برای عامل استفاده کنید. برای مدیریت CA مستقل و محدود ایجاد کنید. عامل‌ها گواهی `serverAuth` با SAN متناسب با آدرس تنظیم‌شده و کنترل‌کننده گواهی `clientAuth` دارد. عامل ایران روی loopback و عامل خارج روی IP مدیریتی خصوصی گوش می‌دهد. فقط کنترل‌کننده به پورت مدیریتی خارج دسترسی داشته باشد. فایل‌های کلید و توکن را با مجوز محدود در `/etc/neo-tunnel/secrets` نگه دارید.
4. روی خارج `neo-probe.service`، هر دو نمونهٔ `neo-frp@frpc-*.service` و `neo-agent.service`، و روی ایران هر دو نمونهٔ `neo-frp@frps-*.service`، `neo-agent.service` و `neo-haproxy.service` را راه‌اندازی کنید. [route.map](examples/route.map) را در `/etc/neo-tunnel/runtime/route.map` و [haproxy.cfg](examples/haproxy.cfg) را در `/etc/neo-tunnel/haproxy.cfg` بگذارید. ورودی نمونه روی `127.0.0.1:16443` است. دسترسی آزمایشی کاربران فقط پس از بررسی مسیرها تنظیم شود.
5. [controller.json](examples/controller.json) را با نشانی‌های عامل‌ها و مشخصات برنامهٔ مقصد تنظیم کنید. نمونه به پاسخ HTTP موفق در `/healthz` با بدنهٔ `ok\n` نیاز دارد. اگر برنامهٔ واقعی پروتکل دیگری دارد، برای آن یک آزمون کاربردی معتبر فراهم کنید و قواعد HAProxy و `app_url` را مطابق همان آزمون تنظیم کنید. نسخهٔ اولیهٔ map باید با `initial` یکسان باشد.
6. روی ایران `neo-watch.service` را راه‌اندازی کنید. پس از دست‌کم ۱۵ دقیقه نمونهٔ پیوسته از هر میزبان، ابتدا `status --json` و سپس `calibrate standby` را اجرا کنید. تغییر تنظیمات frp، HAProxy یا برنامهٔ سلامت را با تغییر `revision` پروفایل در تنظیم کنترل‌کننده ثبت کنید تا شواهد قبلی منقضی شوند.

## کالیبراسیون و انتخاب

- چینش آزمون A/B/A است. هر مسیر ۶۰ تلاش هم‌سایز در چهار مرحله دارد. پاسخ باید دادهٔ ارسالی را کامل بازگرداند. سقف هر اجرا ۵ دقیقه و ۶۴ MiB مجموع دو جهت و همهٔ مسیرهاست. حجم هر درخواست پیش از ارسال از بودجه کم می‌شود تا انتقال ناقص هم سقف ترافیک مفید را رد نکند.
- آزمون به تازه‌بودن داده و بودجهٔ منابع هر میزبان وابسته است. فشار شدید حافظه، OOM، فشار پایدار ۳۰ثانیه‌ای، تغییر شدید بار میزبان یا از دست رفتن سلامت مسیر فعال، شواهد را نامطمئن می‌کند. دادهٔ مدیریتی با عمر بیش از ۳۰ ثانیه نامعلوم می‌شود. HAProxy حتی هنگام قطع کانال مدیریت، مسیرها را مستقل بررسی می‌کند.
- CPU و working set کل ابزار از `neo.slice` خوانده می‌شود. مسیر cgroupهای فرزند را می‌توان در `profile_cgroups` ثبت کرد تا نرخ مصرف و RAM پشتیبان هم جدا در JSON دیده شود. مصرف فرزند در کل slice منظور شده است. سربار شبکه مستلزم `wire_interface` اختصاصی مسیر آزمایش در هر میزبان است. مقدار اندازه‌گیری‌نشده `null` می‌ماند. آمار جزئی و دقیقه‌ای عامل به‌ترتیب در فایل‌های ساعتی ۲۴ ساعت و فایل‌های روزانهٔ هفت روز نگه داشته می‌شود.
- HAProxy پس از سه شکست یا سه موفقیت وضعیت مسیر را تغییر می‌دهد. cadence نمونه به backend وصل است و برای TCP/TLS پنج ثانیه و QUIC پانزده ثانیه می‌ماند، حتی اگر ترجیح عوض شود. `watch` آمار خود HAProxy را می‌خواند. اتصال بازِ سالم هنگام تغییر ترجیح مسیرش را حفظ می‌کند.
- `apply` پیشنهاد را با نسخهٔ جاری و هش تنظیمات می‌سنجد و پس از بررسی پاسخ رفت‌وبرگشت و برنامه، فقط مسیر اتصال‌های جدید را تغییر می‌دهد. `watch` برای ترجیح خودکار دو پروفایل دائمی به شواهد تکرارشده در بازهٔ حداقل پنج دقیقه و پایان فاصلهٔ پنج‌دقیقه‌ای از تغییر قبلی نیاز دارد. گزینهٔ آزمایشی با `apply` فعال می‌شود. دادهٔ ISP و کیفیت واقعی مشتری تا زمان استقرار نقاط آزمایش، نامعلوم است.

## مسیر آزمایشی NaiveProxy

[پیکربندی NaiveProxy](examples/naive) شامل Caddy با forwardproxy و TLS/HTTP2، SOCKS محلی Naive و frp است. Caddy فقط اتصال به `127.0.0.1:17020` را می‌پذیرد. frpc در خارج از SOCKS محلی استفاده می‌کند و همچنان نام میزبان `iran.example.net` و گواهی frps را در TLS داخلی اعتبارسنجی می‌کند. دامنهٔ عمومی پروکسی و گواهی معتبر همان دامنه را تعیین کنید. کاربر و رمز منحصربه‌فرد با حروف و ارقام را در فایل خصوصی `proxy.env` و JSON کلاینت قرار دهید.

backend و قانون frontend نمونه را به HAProxy اضافه کنید. سپس پروفایل سوم زیر را به `profiles` اضافه کنید. مسیر فعلی باید با `replaces` برابر باشد.

```json
{
  "revision": "naive-pilot-v1",
  "carrier": "naive/http2",
  "canary": "127.0.0.1:17122",
  "app_url": "http://127.0.0.1:17121/healthz",
  "app_body": "ok\n",
  "experiment": "transport",
  "staged": true,
  "replaces": "primary"
}
```

unitهای مرحله‌ای و قاعدهٔ polkit در [examples/naive/systemd](examples/naive/systemd) هستند. روی ایران `units` عامل را به `primary: neo-frp@frps-primary.service` و `naive: neo-frp@frps-naive.service` و در خارج به معادل frpc نگاشت کنید. فورواردها و پورت frps آزمایشی خصوصی بمانند. بعد از آماده‌شدن هر دو عامل، `calibrate naive` را اجرا کنید و برای اعمال از شناسهٔ پیشنهاد واجد شرایط استفاده کنید. مسیر قبلی تا پایان مشاهده و تخلیهٔ نشست‌های TCP حفظ می‌شود. توقف خودکار مسیر قبلی برای پایلوتی است که ورودی مشتری آن TCP در HAProxy است. پیش از استفادهٔ مستقیم مشتری از پورت‌های فرعی UDP، سیاست بازنشستگی آن مسیر را جداگانه طراحی کنید. پس از ریبوت میزبان، unitهای فعال و وضعیت park را از روی `status` و `systemctl` تطبیق دهید.

## آزمایش‌های بازتولیدپذیر

نسخه‌های آزمایش frp 0.72.0، HAProxy 3.4.7، NaiveProxy v154.0.8037.49-5 و Caddy forwardproxy v2.11.7-naive2 هستند. برای انتشار عمومی بازبینی نسخه و اصلاحات امنیتی لازم است. [frp](https://github.com/fatedier/frp/releases/tag/v0.72.0) · [HAProxy](https://www.haproxy.org/download/3.4/src/) · [NaiveProxy](https://github.com/klzgrad/naiveproxy/releases/tag/v154.0.8037.49-5) · [Caddy forwardproxy](https://github.com/klzgrad/forwardproxy/releases/tag/v2.11.7-naive2)

```sh
python3 tests/lab.py --frp-dir /path/to/frp --haproxy /path/to/haproxy --probe build/native/backhaul-probe

docker build -t neo-tunnel-lab -f tests/Dockerfile tests
# مسیر FRP_LAB_BIN را به پوشهٔ باینری‌های لینوکس frp تنظیم کنید.
docker run --rm --privileged --network none --entrypoint python3 \
  -v "$PWD:/project:ro" -v "$FRP_LAB_BIN:/frp:ro" neo-tunnel-lab \
  tests/lab.py --netns --frp-dir /frp --haproxy /usr/local/sbin/haproxy \
  --probe build/linux-arm64/backhaul-probe --controller build/linux-arm64/neo-tunnel
```

مسیر `linux-arm64` را متناسب با معماری کانتینر تعیین کنید. سناریوی کنترل‌کننده برای تکرارپذیری تله‌متری mTLS آزمایشی می‌فرستد. `tests/agent_lab.py` جداگانه عامل واقعی و cgroup را در کانتینر Linux با شبکهٔ قطع و cgroup namespace خصوصی می‌آزماید. `tests/naive_lab.py` به باینری‌های Naive، Caddy forwardproxy و frp هم‌معماری کانتینر نیاز دارد. هیچ‌یک از تست‌ها به سرور واقعی متصل نمی‌شوند.

## پذیرش میدانی

مرحلهٔ هفت‌روزه و آزمون بار نماینده در ۲۵٪، ۵۰٪ و ۱۰۰٪ اوج به VPS ایران و خارج، مشخصات پنل و سرویس مقصد، ترافیک نمونه و ورودی‌های اپراتوری نیاز دارد. طی آزمایش آن را کنار ورودی موجود اجرا کنید. ظرفیت و تجربهٔ مشتری باید روی همان دو میزبان با مسیر موجود مقایسه شوند.
